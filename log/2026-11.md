# 2026-11

## 2026-11-22｜meta 仓库补齐工程控制策略（一整轮复盘）

**触发**：owner 问「meta 自己没开 PR 么」。查下来不只是 PR——`has_pull_requests: false`、`has_issues: false`、rebase 合并开着，而且它根本没登记进 `github-policy.json`，校验脚本从来不检查它。

### 这轮实际做了什么

1. **meta 自身**：开 PR / Issue、改仅 squash、合并后删分支；免费私有仓库拿不到的分支保护 / ruleset / tag 保护按 F2 记「不可用」，并加反向断言（一旦可读就报「记录已过期」）。
2. **名单合一**：README 成为唯一登记处（新增 `GitHub 策略` 列 + 本仓库一行），`github-policy.json` 只写期望值并删掉 `repo` / `private`，两边对不上直接失败。
3. **档位收口**：发现「精简」与「全量」的检查项完全相同 → 删掉该值，脚本只接受 `全量` / `不套用`。
4. **`.DS_Store`**：契约检查读文件系统、不经过 git，Finder 一写就误报五个项目全红 → 脚本遍历跳过 + 仓库 gitignore + 本机全局 gitignore。
5. **临时产物**：agent 把脚本丢在 `/tmp`，和其他会话的文件混在一起差点误删 → 立 E25，产物放工作区 `TEMP/`、收尾清空。
6. **共享层同步**：三次（`d506bc9` → `49ce846` → `3185571`），每次 5 个项目各开一个 PR。
7. **收尾**：`check-github-policy` OK (6)、`check-project-contract` OK (5)，六个仓库只剩 `main`。

### 走过的弯路

- **先说「meta 没有 PR 功能」**：其实是仓库设置里关掉了，不是平台不支持。把「能力不存在」和「开关关着」混为一谈，会导错方向。
- **一度打算把 meta 公开**，方案都排到「清历史 + 上 CI」了，最后发现 README 里登记着私有仓库名——公开等于公开私有仓库地图，撤回。
- **两份名单并行了半天**：改 README 和改 json 各写一遍，直到 owner 要求「不能有两份名单」才合并。
- **`.DS_Store` 修了两次**：第一次只加 gitignore，发现不解决误报，才去改脚本——诊断阶段没搞清「谁在读文件」。
- **`/tmp` 这件事**：README 里早写着 `TEMP/` 是放临时文件的，但只写了「是干嘛的」、没写「必须这么做」，于是它不构成约束。

### 没解决的

- meta 的「只能靠 PR」是流程约束，不是机制强制（F2）。要机制强制只能公开或买 Pro，owner 选择维持现状。
- 账户下另有 4 个仓库明确不纳入（其中 1 个私有，名称从略），任何校验都不覆盖它们。
- 档位删掉「精简」后只剩「全量 / 不套用」，没有更细的分级；真需要分级时要重新设计，不是加个标签。

### 如果重来

- 先问清「这个仓库属于哪一档、要不要纳入策略」，再动手配置——先配后补登记会返工。
- 改共享层之前先算清项目同步的成本；能合并成一次改的就别拆成三轮。
- 遇到「看起来是平台不支持」的现象，先查一次 API 原始返回值，再下结论。
